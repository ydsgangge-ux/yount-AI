========================================================
Dungeon Agent 开发文档
========================================================
版本: v0.1（设计讨论稿）
关联系统: Story Agent / Party Agent / CombatSystem


--------------------------------------------------------
一、核心定位
--------------------------------------------------------

Dungeon Agent 的职责边界必须严格限定为：

    只负责"布置和设定"，不负责"剧情"。

具体来说：

- 它不决定"为什么这里现在会出现一个地下城/威胁"——这是上游判定层的事
- 它不写玩家看到的叙事文本、对话、场景描写——这是 Story Agent 的事
- 它只做一件事：把上游给的"布防指令"，翻译成结构化的空间/数值数据

这个边界存在的原因：如果同一个 agent 既设计地下城机关又扮演讲故事/引导
玩家的角色，它天然知道所有答案，等于开天眼，是作弊。Dungeon Agent 必须
是一个"哑巴执行者"——生成数据，但不参与因果、不参与叙事。


--------------------------------------------------------
二、上游：判定层（不属于 Dungeon Agent，但是它的输入来源）
--------------------------------------------------------

判定层的职责是决定"现在该不该有、该有一个什么规模/性质的地下城"。
根据世界类型不同，判定层的实现方式不同：

1. 游戏向异世界（副本可刷新型）
   判定层可以是相对固定的世界设定表——比如某个地点本来就设计了一个
   副本，规则简单，判定层输出基本是静态配置。

2. 生存向异世界（无地下城固定性，偏剧情战略）
   判定层是一个持续运行的"世界威胁/势力状态机"——例如 Boss 是否已
   经把周边据点的兵力集结到了一起，这是随玩家行动/时间推移持续演化
   的世界状态，不是玩家一进入就固定生成的实例。

两种判定层最终都要产出同一种东西喂给 Dungeon Agent：

    【布防指令 Deployment Order】（示意字段，实际字段待定）
    {
      "location_ref": "...",       // 地点标识
      "threat_scale": "...",       // 规模/强度
      "urgency": "...",            // 紧迫度（影响是否已完全成型）
      "world_ref": "...",          // 属于哪个世界观，供取用素材
      "trigger_reason": "..."      // 事实性触发原因（不是剧情文本，只是标记，
                                    //  例如 "boss_mobilization" / "fixed_farm_dungeon"）
    }

注意：Deployment Order 只包含事实性字段，不包含叙事文本。"这里为什么存在"
这种黑石塔式的历史/身份细节，由 Dungeon Agent 自己结合世界观设定推导填充，
判定层不越权代劳，否则判定层又会变成半个编剧。


--------------------------------------------------------
三、Dungeon Agent 内部三种调用
--------------------------------------------------------

3.1 Generator（生成调用）—— 一次性，之后不再重跑

    触发时机：地下城/楼层首次被进入前（懒加载，走到哪补到哪）
    输入：Deployment Order + 世界观素材库 + 玩家当前状态（等级/已选择路径摘要）
    输出：结构化数据，写入后不可变（锁定）

    生成分两层：

    (a) 骨架层 Skeleton —— 一次性生成，永久不变
        - 叙事身份（这个地方是谁建的/为什么存在/关键历史锚点，1~3个）
        - 阵营/生态逻辑（谁占据这里、内部是否有矛盾可利用）
        - 房间图拓扑（连接关系、楼层数、Boss 房位置）
        - 每个房间的"叙事角色"标签（例如"曾经的议事厅，现已废弃"），
          不是功能标签（陷阱房/宝藏房），功能要从叙事角色自然推导

        参照标准：WoW 黑石深渊/黑石塔式设计——地下城本身要有存在理由，
        不是为了放怪而拼凑的空房间。

    (b) 内容层 Content —— 懒加载，走到哪个房间生成哪个房间，生成后锁定
        - 具体机关（陷阱位置、触发条件、部位伤害）
        - 怪物配置、掉落物
        - 必须服从骨架层给定的叙事角色，不能违和

    文件持久化：一个地下城对应一个文件，例如：
        /dungeons/{dungeon_id}.json
        {
          "skeleton": { ... },              // 锁定，不再变
          "rooms": {
            "room_001": {"generated": true, "hazards":[...], "loot":[...]},
            "room_002": {"generated": false} // 骨架已知存在，内容待生成
          },
          "boss": { ... },
          "discovery_state": { ... },        // 唯一持续可变的部分，见 3.3
          "spawn_table": { ... }             // 游戏向专用，见四
        }

3.2 Referee（裁判调用）—— 极少触发，只处理"意外行动"

    多数玩家行动应该是代码对已锁定数据做查表判定（踩到的位置是否匹配
    已记录陷阱坐标），不需要调用 LLM。

    只有当玩家做出生成数据没有预料到的自由行动时（例如"往符文上倒水"），
    才触发 Referee 调用去解释这个行动的后果。

    输出：结构化 delta（不是叙事文本），例如：
        {"triggered": true, "damage": 12, "newly_revealed": ["trap_003"]}

    这个 delta 写回文件（视为对锁定数据的补充判定，避免下次问同样问题
    得到不同答案），然后交给 Story Agent 去写成玩家看到的文字。

3.3 发现状态维护 —— 持续可变，不锁定

    discovery_state 记录"谁已经发现了什么"，按观察者（玩家/各队友）分别
    维护，支持"某队友提前察觉陷阱"这类差异化感知：

        "discovery_state": {
          "player": {"trap_003": true},
          "party_member_1": {"trap_003": false}
        }

    这是文件里唯一允许运行时持续修改的部分，骨架和内容一旦生成不再改动。


--------------------------------------------------------
四、游戏向 vs 生存向的差异（仅影响判定层和刷新逻辑，不影响 Dungeon Agent 核心）
--------------------------------------------------------

游戏向异世界：
    - 判定层相对静态，副本可重复进入
    - Dungeon Agent 生成的骨架/内容依然锁定不变
    - 额外叠加一层 spawn_table（刷新表）：小怪可重置刷新，
      但房间结构、机关、Boss 身份不受影响——刷新的只是"谁站在这个房间"，
      不是空间本身

生存向异世界：
    - 判定层是持续演化的世界威胁状态机（可能是独立 Threat Agent，也可能
      并入 Story Agent 管理的世界状态），主动演化，不依赖玩家进入才触发
    - Dungeon Agent 依然只在被触发时生成一次性的"当前局面"布置，
      生成后同样锁定，不因为威胁状态机后续变化而重新生成已锁定的内容
      （如果威胁状态机产生新的重大变化，应该视为触发了一个新的
      Deployment Order，走一次新的生成，而不是回头修改旧数据）


--------------------------------------------------------
五、与其他系统的接口
--------------------------------------------------------

- 对 Story Agent：Dungeon Agent 输出结构化数据（骨架/内容/裁判delta），
  Story Agent 消费这些数据生成玩家看到的所有文本，Dungeon Agent 不直接
  产出任何叙事文案

- 对 Party Agent：队友决策只能读"观测视图"——即骨架/内容中
  revealed=true（或 discovery_state 中标记为该观察者已发现）的部分，
  隐藏字段不会出现在 Party Agent 的输入里，物理上无法泄露

- 对 CombatSystem：Dungeon Agent 只提供敌人/Boss 的初始数值配置，
  不参与战斗数值计算，所有伤害/硬直/命中判定统一走 CombatSystem，
  避免多处各自计算导致状态不一致


--------------------------------------------------------
六、实现顺序建议（避免一次性实现全套导致难产）
--------------------------------------------------------

不建议一开始就实现完整的多 agent 流程，建议分期：

第一期：只做 CombatSystem + 手写 1-2 个固定副本 JSON
        （人工模拟 Dungeon Agent 的输出，验证战斗手感）

第二期：接入 Story Agent 叙事，验证"锁定数据 + 动态叙事文本"组合体验

第三期：实现 Dungeon Agent 的 Generator，先只做游戏向（相对简单、
        判定层静态、不涉及持续演化的威胁状态机）

第四期：接入 Party Agent + 观测视图过滤机制

第五期（可选，可延后）：生存向的世界威胁状态机


--------------------------------------------------------
