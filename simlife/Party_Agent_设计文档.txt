========================================================
Party Agent 开发文档
========================================================
版本: v0.1（设计讨论稿）
关联系统: Dungeon Agent / Story Agent / CombatSystem


--------------------------------------------------------
一、核心定位
--------------------------------------------------------

Party Agent 负责模拟队友，职责边界：

    只负责"队友该做什么决策、说什么话"，不负责判定世界真相。

关键前提：Party Agent 和玩家处于同一信息水平——它不能访问 Dungeon
Agent 掌握的隐藏真相（陷阱位置、Boss 弱点等未 revealed 的字段）。
这不是靠 prompt 叮嘱"别偷看"，而是架构上保证：Party Agent 的输入
只有"观测视图"，隐藏字段从数据层面就没有进入它的上下文，想泄露也
做不到。

这个前提存在的原因：如果队友对局势了如指掌、从不误判，会显得像开
了透视挂，破坏"没人知道会发生什么"这个核心体验（呼应 Story Agent
"随机生成场景、用户和系统角色都不知道会发生什么"的设计）。队友应该
和玩家一样会踩坑、会误判、会因为看不到全局而做出不完美的决定。


--------------------------------------------------------
二、队友"人格"不是固定模板
--------------------------------------------------------

明确排除的方案：不做"坦克/输出/治疗"这种固定 AI 模板式队友。

队友的战斗决策应体现在应对具体局面时的选择上，而不是被预先写死的
角色定位框住。具体决策依据：

- 队友当前能看到的观测视图（和玩家一致的那份，或按观察者过滤后
  略有差异的那份，见第四节）
- 队友与玩家/其他队友的关系状态（影响是否舍身支援、是否优先自保）
- 当前战斗状态（自身HP、架势值、是否处于硬直）

决策落地到 CombatSystem 的具体动作：
    - 攻击 / 防御方式选择（闪避 / 格挡 / 招架 / 不设防）
    - 技能使用时机
    - 目标选择（攻击哪个敌人、支援哪个队友）


--------------------------------------------------------
三、决策与执行严格分离
--------------------------------------------------------

Party Agent 只做"决策"，不做"数值计算"：

    Party Agent 输出：结构化决策
        {
          "actor": "party_member_1",
          "action": "block",          // 对应 CombatSystem 的 DefenseAction
          "target": "enemy_002",
          "reason_tag": "..."         // 供内部记录，非叙事文本
        }

    CombatSystem 执行：伤害/硬直/命中判定，是唯一的数值计算来源

这样做的原因：如果 Party Agent 自己算伤害，容易和 Dungeon Agent /
Referee 各算一套，导致同一场战斗里状态不同步。所有角色（玩家、队友、
敌人）的数值结算必须走同一套 CombatSystem，Party Agent 的职责到"选
哪个动作"为止。


--------------------------------------------------------
四、观测视图与差异化感知（可选，视复杂度决定是否实现）
--------------------------------------------------------

基础版本：所有队友和玩家共享同一份观测视图，队友的"不同"只体现在
关系状态和当前战斗数值上，不体现在信息量上。

进阶版本：不同队友可以有各自独立过滤出的观测视图，支持"某队友提前
察觉了一个陷阱，玩家没发现"这类差异化感知。这依赖 Dungeon Agent 的
discovery_state 已经是按观察者分别维护的（见 Dungeon Agent 文档三.3），
Party Agent 只需要按 actor_id 去查对应的那份视图，不需要额外设计新
机制。

建议先实现基础版本（共享视图），进阶版本留到基础流程跑通之后再加。


--------------------------------------------------------
五、台词/反应生成 与 决策生成 是否要拆成两次调用
--------------------------------------------------------

参照 Dungeon Agent 的 Referee/Narrator 分离经验，建议同样拆开：

    (a) 决策调用：输入观测视图 + 队友状态，输出结构化动作
        （轻量，可用较小/较快模型，甚至部分场景可规则引擎化）

    (b) 台词/反应调用：基于已决定的动作 + 当前场面，生成队友的
        对话/反应文本（这部分需要 Story Agent 或类似质量的模型
        来保证文字水准）

拆开的理由：如果一次调用既要"决策"又要"生成有文采的台词"，成本和
延迟会叠加在一起（尤其一场战斗多名队友、多个回合、每回合都要调用）。
拆开后，决策部分可以做得很轻量甚至规则化，只有真正需要文字质量的
台词部分才用重模型。

注意：台词生成阶段同样只能看观测视图，不能看隐藏真相——即使决策
已经做出，台词也不能"剧透"队友决策背后的真实原因（如果那个原因涉
及尚未 revealed 的信息）。


--------------------------------------------------------
六、与其他系统的接口
--------------------------------------------------------

- 对 Dungeon Agent：只读取其暴露的观测视图（骨架/内容中已 revealed
  的部分，或按 discovery_state 过滤后的部分），不直接访问锁定文件
  的完整内容

- 对 Story Agent：Party Agent 产出的台词/反应文本，视为素材的一部分，
  最终由谁来呈现给玩家（Story Agent 直接输出，还是先汇总）待实现时
  确定，但决策逻辑本身不依赖 Story Agent

- 对 CombatSystem：Party Agent 只提交结构化动作请求，不参与任何伤害/
  状态计算，结算结果（HP变化、硬直触发等）由 CombatSystem 返回后，
  Party Agent 在下一轮决策时读取最新状态


--------------------------------------------------------
七、成本控制注意事项
--------------------------------------------------------

多队友场景下，如果每个队友每回合都触发"决策+台词"两次 LLM 调用，
调用量会随队友数量线性增长，容易拖慢战斗节奏。建议：

- 决策调用优先规则引擎化（人格倾向加权表 + 当前局势输入 → 输出动作），
  不是所有队友决策都要走 LLM
- 台词调用可以不是每回合都触发，只在关键节点（硬直触发、濒死、
  Boss阶段切换等）才生成台词，日常普通攻击回合可以只用简短的固定
  反应模板或干脆不出台词


--------------------------------------------------------
八、待定问题（尚未拍板，需要后续讨论）
--------------------------------------------------------

1. 决策调用具体用规则引擎还是轻量 LLM，需要实际测试手感后决定
2. 台词触发的"关键节点"具体范围，需要实测调整
3. 队友是否会真正死亡（永久损失）——此前讨论中尚未定论，会直接影响
   Party Agent 决策逻辑里"风险规避"权重该怎么设
